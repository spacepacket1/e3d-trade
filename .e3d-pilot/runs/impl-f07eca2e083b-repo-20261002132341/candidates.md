# Candidates

## Proposed Candidates

### Candidate flow-only-small-size-1: Re-admit thin-evidence (flow-only) MOVER/SURGE entries at a small, capped position size instead of blocking them outright
Duplicate: no
Dedup rationale: Not a reversal of the just-merged idea-fc54d003c5f5/PR#5 -- that PR correctly closed a loophole where a MOVER/SURGE story counted as its own independent evidence, which is still a real bug and stays fixed. This candidate changes what happens to a candidate that is correctly classified flow_only: instead of SCOUT_FLOW_ONLY_PER_CYCLE_LIMIT=0 blocking it completely, let a small number through per cycle at a small, explicit position-size ceiling. Reuses the exact same evaluateScoutPacketEligibility/scoreEvidencePacket flow_only computation from scripts/evidencePackets.js -- no new signal, no new evidence source_type.
Category: risk/strategy
Analogy: evidence-based iteration and experiment design (right-skewed/fat-tailed bet sizing -- small stake per trial, let a rare outsized winner carry the category, rather than trying to pre-screen for winners with signals that don't actually predict them)
Attraction (1-5): 4
Retention (1-5): 3
Effort: 2
Revenue (1-5|n/a): 3
Description: CONTEXT (direct follow-up to idea-fc54d003c5f5 / PR#5, same day): after merging the fix that stops a MOVER/SURGE story from self-satisfying Scout's evidence-quality gate, the user pointed out that QNT -- bought 2026-09-16 on exactly a thin-evidence MOVER story with no other backing -- was e3d-trade's single best trade (+$16,839.51 realized, the trade that turned the book from losing money for months to strongly profitable in days) and asked to restore the ability to catch another one.

Investigation (full historical pull, done today): of 81 historical MOVER/SURGE buys matched to realized outcomes, those WITH measured dex-flow data (buy_sell_ratio_1h present, n=8) returned -$55.63 total, 12.5% win rate -- notably, several of these already cleared the existing buy_sell_ratio_1h>=3.5 threshold and still lost money, so that threshold does not predict outcomes even on its own terms. Those WITHOUT measured dex-flow data (n=34, QNT's cohort -- QNT's own _dex_flow was literally null, not a real zero; the 'b/s 1h 0' text in its why_now field was a missing-data placeholder) returned +$16,582.95 total, 26.5% win rate -- but excluding QNT alone, that same cohort returns -$256.57, 24.2% win rate, statistically indistinguishable from the has-flow-data losers (median pnl ~-$7 to -$8 in both groups). Conclusion, confirmed with the user: no signal available at entry time (liquidity, volume, market cap, or dex buy/sell flow ratio) distinguishes a QNT-type winner from the ~75-88% of thin-evidence MOVER/SURGE entries that lose a small amount. This category is a right-skewed, low-win-rate bet whose positive expectancy (if any) depends entirely on rare, outsized winners. The right lever for that shape is position size, not a smarter quality filter -- confirmed as the user's explicit decision.

SCOPE:
1. In scripts/evidencePackets.js, change `SCOUT_FLOW_ONLY_PER_CYCLE_LIMIT` from 0 to 1 (exactly one flow-only candidate may reach Scout's shortlist per cycle, so the book cannot fill up with many thin-evidence bets in a single cycle).
2. In `flowOnlyPasses` (evaluateScoutPacketEligibility, scripts/evidencePackets.js ~line 757-761): remove the `metrics.buy_sell_ratio_1h >= SCOUT_FLOW_ONLY_MIN_BUY_SELL_RATIO_1H` condition entirely -- data shows it does not predict outcomes and is frequently unavailable (null/NaN, not a real measured value) for larger, more established tokens like QNT that simply are not covered by whatever dex-flow-tracking source populates `_dex_flow`. Change the flow_signal check so a MISSING flow_signal (no measured value at all) passes, and only an EXPLICITLY distribution-labeled flow_signal fails it -- i.e. `(!metrics.flow_signal || !metrics.flow_signal.includes('distribution'))` in place of the current `metrics.flow_signal && !metrics.flow_signal.includes('distribution')`. Keep `SCOUT_FLOW_ONLY_MIN_LIQUIDITY_USD`, `SCOUT_FLOW_ONLY_MIN_VOLUME_24H_USD`, and `SCOUT_FLOW_ONLY_MIN_MARKET_CAP_USD` and their comparisons completely unchanged -- these are the real safety filter (can this position actually be sized and exited safely) and stay exactly as they are. Do not remove or rename `SCOUT_FLOW_ONLY_MIN_BUY_SELL_RATIO_1H` itself (keep the now-unused export for backward compatibility with anything else that might import it -- check for other importers before deciding whether it can be fully removed).
3. Add a new `flow_only_max_position_pct` field to `SETTINGS_DEFAULTS` in pipeline.js, defaulting to `0.015` (1.5% of equity), placed near the existing `max_position_pct: 0.12` definition with a comment explaining it is the ceiling for a flow_only-classified new entry specifically.
4. Ensure the flow_only classification computed in `buildScoutEvidenceShortlist` (via `rankScoutPacket`/`evaluateScoutPacketEligibility`) reliably survives into the proposal object that reaches `evaluateBuyActions`, so sizing can act on it. Investigate and use whichever existing propagation path already carries packet-level evidence metadata onto a proposal (`extractEvidenceMetadata`/`applyEvidenceMetadata`, `evidence_summary.warnings` containing `flow_only_candidate`, or an equivalent already-wired field) -- if tracing shows this is NOT reliably populated end-to-end today for a fresh scout_candidate buy proposal (verify against this repo's own recent training-events.jsonl risk_decision records, not assumption), fix that propagation explicitly as part of this change so it is reliable going forward. Do not invent a second, differently-computed flow-only heuristic at buy-evaluation time -- there must be exactly one place that decides flow_only, and every consumer reads that same decision.
5. In `evaluateBuyActions` (pipeline.js), for a ranked candidate that is a NEW entry (not an existing-position add) and is classified flow_only per step 4: cap `allocationUsd` at `eq * settings.flow_only_max_position_pct` in addition to (not instead of) every existing cap (cash, category headroom, min_trade_usd, the risk engine's approved_size_pct, max_position_pct). The smallest of all applicable caps wins, exactly like today's existing cap-stacking pattern. A flow_only candidate must still pass every other existing deterministic check (deterministicBuyGate, risk review, category cap, fraud risk, etc.) -- this candidate only changes sizing and the per-cycle admission cap, nothing else.
6. Do not apply `flow_only_max_position_pct` to a pyramid-in add (that path already has its own, separately-shipped sizing/headroom logic from PR#5) -- this only caps a brand-new flow_only position's initial size.
7. Extend `scripts/verifyEvidencePackets.js` with regression coverage: a packet shaped like QNT's actual historical proposal (MOVER story only, no thesis/candidate/watchlist, `_dex_flow` null/absent, liquidity $199,244, volume_24h $134,777, market_cap $887,545,978) must now evaluate `flow_only: true` AND `flow_only_passes: true` (it was `flow_only_passes: false` before this change, solely because of the removed buy_sell_ratio_1h requirement). Also assert a packet with an explicitly distribution-labeled flow_signal still fails `flow_only_passes` regardless of liquidity/volume/market_cap, and a packet failing any one of the three remaining minimums still fails `flow_only_passes`.
8. Extend the buy-evaluation test suite (wherever PR#5's `evaluateBuyActions` tests live, e.g. `scripts/verifyScoutRelaxation.js`) with: a flow_only-classified new-entry candidate whose risk-approved size would otherwise exceed `flow_only_max_position_pct` gets capped at exactly that ceiling; a flow_only candidate whose risk-approved size is already below that ceiling is unaffected; a non-flow_only candidate's sizing is completely unchanged by this cap; and a second flow_only candidate in the same cycle is blocked by the per-cycle limit (now 1, was 0) rather than also being sized and bought.

NON-GOALS (explicitly out of scope -- do not implement):
- Changing SCOUT_FLOW_ONLY_MIN_LIQUIDITY_USD, SCOUT_FLOW_ONLY_MIN_VOLUME_24H_USD, or SCOUT_FLOW_ONLY_MIN_MARKET_CAP_USD.
- Any change to position identity resolution, cooldowns, pyramid-in sizing/headroom, or target/partials-taken handling shipped in PR#5 -- all of that stays exactly as merged.
- Any new evidence source_type, story/thesis scoring, or signal_snapshot change.
- Raising SCOUT_FLOW_ONLY_PER_CYCLE_LIMIT above 1, or changing max_position_pct, category_cap_pct, or any other existing cap.
- Harvest/exit logic, governance, reconciliation, or sidecar evidence behavior.
