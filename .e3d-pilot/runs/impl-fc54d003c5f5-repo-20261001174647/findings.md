ROOT CAUSE (found by reading the actual code, not guessing): evaluateScoutPacketEligibility (scripts/evidencePackets.js line ~724) computes `isFlowOnly = packet.story_evidence_count === 0 && evidence.some(item => item.source_type === 'flow')`. packet.story_evidence_count (scoreEvidencePacket, same file, line ~565) counts ANY evidence item with source_type in ['story','thesis','watchlist'] -- with NO distinction between a genuine pre-pump/analytical story (STAGING, CLUSTER, SMART_MONEY_LEADER, THESIS, etc.) and a MOVER or SURGE story. In pipeline.js's buildScoutEvidenceShortlist (line ~5162: `evidence.push(...stories)`), the very MOVER/SURGE story that caused Scout to notice the token in the first place gets pushed into that token's own evidence packet as a source_type:'story' item (built by buildScoutStoryEvidence, pipeline.js line ~4970, which does tag it with a `story_type` field and correctly marks its `direction` as 'bearish' per pipeline.js's existing `lateSignalTypes = new Set(['MOVER','SURGE'])` at line ~3983 -- but that story_type/lateSignal distinction is never consulted by story_evidence_count or isFlowOnly). The result: a MOVER/SURGE story self-satisfies the 'do you have independent story backing' check, making story_evidence_count >= 1, making isFlowOnly false, completely bypassing the SCOUT_FLOW_ONLY_PER_CYCLE_LIMIT=0 cap -- for exactly the category of candidate that cap exists to catch. This is a one-line-root-cause bug in an otherwise well-designed and already-correct system.
